Calibrate the instrument before you trust the number

Your spec calls Milestone 0 the thing to do “before anything else.” It is right, and for a sharper reason than it says: I ran it, and the scorer failed all 40 tasks on SQL that was perfectly correct.

Why this one

You are about to produce a number — Mode A scores x, Mode B scores y — and build a write-up on the gap between them. Two things can make that gap meaningless, and neither announces itself:

  1. The instrument is miscalibrated. The scorer disagrees with ground truth for reasons having nothing to do with the agent.
  2. The instrument is fine but you varied more than one thing. The gap is real and measures something other than what you claim.

Milestone 0 kills the first. The second needs an argument, and most of this lesson.

Before you read on — retrieval practice

You wrote in CLAUDE.md: “hold everything else fixed: same model, same prompts, same task order, same max_steps, same temperature. Only the checkpoint mechanism varies.” From memory: name everything else that will differ between your Mode A and Mode B runs. Thirty seconds.

Now compare

There are at least four beyond your list, and one of them is unavoidable by construction — you cannot hold it fixed, only measure around it. Section “What else is in this category?” below.

What Milestone 0 actually caught

Three findings from one run. The first is the one that would have cost you a weekend.

1 · The scorer failed 40/40 on correct SQL

FAIL #34 [UPDATE] Basketball Tournament Results
  want [('6e5be5df6a81c825cba000c75965d27f',)]
  got  (('6e5be5df6a81c825cba000c75965d27f',),)

The MD5s are identical. The gold SQL was right, the hash was right, the table state was right. AgentBench built answer_md5 with str(cursor.fetchall()) on a driver whose fetchall() returns a list; pymysql returns a tuple. Same bytes, different repr, string comparison fails, everything fails.

# the entire fix
return str(list(cur.fetchall()))
Sit with this one

A scorer that reports 0% for a perfect agent is not obviously broken — it looks like a hard benchmark. Had you built the agent first and run the scorer second, the natural reading of 0/40 is “the model is bad at this,” and you would have spent the weekend tuning prompts against an instrument that could never return a pass. Milestone 0 is not bookkeeping. It is the difference between a result and a wasted weekend.

2 · The group_concat bug is real, and does not bite

Your spec flags group_concat_max_len as “a latent correctness bug in the reference scorer — worth confirming.” Confirmed, both directions:

group_concat_max_lenResultReading
default (1024)40/40Identical. Not binding here.
1 048 57640/40
64 (forced)wrong hash, no error The failure is real and silent when reached.

Measured table sizes: min 12 rows, max 44. At 5 chars + 1 separator per row, truncation begins around 170 rows — a 4× margin. So: the bug exists, it is silent, and this dataset does not reach it. That sentence is worth more in a write-up than either half alone, because it shows you checked rather than assumed.

3 · Gold SQL executes in ~0.9 ms

Median across 40 tasks. Useful as your denominator: any checkpoint mechanism costing more than a millisecond is already dominating the work it protects.

What else is in this category?

Last session you found the DDL guard yourself, then stopped at DDL — when three of the four savepoint killers are not DDL. Same move applies here. Your CLAUDE.md list is correct and incomplete:

The move worth stealing

Mode A′ — the placebo. Identical tool schema and system prompt to Mode B, but checkpoint() and restore() do nothing and always report success. Then A′ − A is the cost of merely mentioning checkpointing, and B − A′ is the mechanism. Two extra runs, no new machinery, and it converts “Mode B scored higher” into a claim about checkpointing specifically. Reviewers who build systems ask for this; getting there first is the difference between a starter task and a research note.

What 40 tasks cannot support

Because the design is paired, only discordant tasks carry signal — the ones where the two modes disagree. Everything both modes pass, or both fail, is noise-free and information-free. Under the exact paired test:

B winsA winsTwo-sided pReportable?
60≈ 0.031Yes
50≈ 0.063No — borderline
31≈ 0.625No — nothing at all

So the honest threshold is roughly six clean flips in one direction. Below that you have an anecdote, and the correct move is to say so and pivot the write-up's weight onto the mechanism argument and the cost measurements — which do not depend on N.

State the rest explicitly, before a reviewer has to: 40 tasks, one benchmark, one model, one schema shape (single table, all columns TEXT, 12–44 rows). Nothing here generalises to multi-table transactions, large data, or concurrent writers. Naming your limits is not a weakness in a write-up; it is the strongest available evidence that you understand your own result.
