The scorer doesn't know the agent exists

You asked how to score an incomplete task. The honest answer is that the question dissolves — and once it does, four of my six exit paths go with it.

Two things wrong with the first version

It was built for the wrong phase. Graceful degradation across six exit paths is what an unattended production run needs. You will be sitting there watching 40 tasks. In that setting graceful degradation turns bugs into data points — the exact failure Lesson 05 warned about, which I then built into the harness.

It was overloaded. Ordering, six exit paths, prompt design and a dry-run harness is four concepts, against a rule of one. “There is a lot I don't understand” was the correct reaction, and it was a drafting failure, not a reading one.

Your question, answered directly

The scorer runs this against the table and compares the string to answer_md5:

SELECT md5(group_concat(rowhash ORDER BY rowhash)) FROM (
  SELECT substring(MD5(CONCAT_WS(',', `col1`, `col2`, ...)), 1, 5) AS rowhash
  FROM `table name`
) AS sub;

Nothing in there refers to an agent. It doesn't know whether one ran, whether it finished, how many turns it took, or which mode it was. It hashes rows.

So there is no “how do we score an incomplete task” rule to design. There is only what is on the table when we hash it — and on a non-happy path you never get there, because you stopped to look. You don't score tasks. You hash tables.

Three outcomes

#OutcomeWhat happens
1commit_final_answerHash the table, compare, record
2anything unexpectedRaise. Stop the process, read the trace, fix it
3max_steps without committingRaise. Stop, read the trace

No fourth bucket. No “excluded as harness artifact”, no partial credit, nothing silently absorbed into a results column. During development every non-happy path is a bug you can still fix, and a harness that keeps going is a harness that hides them.

Two postures, and you can only design one of them now
Debugging (now)Crash loudly. Every non-happy exit is fixable.
Measurement (later)Tolerate whatever survived fixing.

You cannot design the second first, because you don't yet know which failures are irreducible. My guess after debugging: max_tokens is fixable (raise it), refusal never fires on these tasks, end_turn is rare enough to be worth stopping for. What's left is max_steps — your outcome 3.

Strict mode: start by crashing on the agent's SQL too

One case sits on the line. If the agent writes UPDATE nonexistent SET ..., is that a bug or normal behaviour?

Eventually, normal — the tool contract is to hand the error back so the agent can react. But during development it usually means your prompt or tool description is wrong, and you want to know now. So the loop takes a flag:

Agent SQL errorsUse when
strict=True (default)RaiseUntil the run is clean
strict=FalseReturn the error as a tool resultOnce you know the errors are the agent's, not yours

What survives from the first version

Only the ordering, and only because each line is forced by something you already established:

  1. CREATE TABLE and INSERT — DDL implicitly commits, so it must precede START TRANSACTION or it destroys the savepoint (Lesson 01).
  2. Mode B: START TRANSACTION, then SAVEPOINT sp_0 — the restore floor, so “reset to start” never needs a bare ROLLBACK (Lesson 04).
  3. The loop.
  4. Commit, then hash on the same connection — a reconnecting scorer reads pre-transaction rows and reports a false negative (Reference 01).
  5. DROP DATABASE.

The “commit, don't roll back at max_steps” section is gone. It solved a problem your model deletes: the only case where it mattered was Mode B running out of turns having already produced the right state — which is something you debug, not score.

The trace is still written up to the crash

Crashing loudly and capturing everything are not in tension — they are the same posture from two sides. The loop stops; the trace file already on disk is how you find out why. This is what the flush-every-line rule from Lesson 05 was for.

Capture maximally, handle minimally. Lesson 05 got the first half right and this lesson got the second half wrong.

Check yourself

Q1The scorer hashes the table. It knows:

  • Nothing about the agent's progress
  • Whether the agent called commit
  • How many turns were used
  • Which mode produced the state

Q2The agent hits max_steps during development. You should:

  • Stop and read the trace
  • Score it as a failure
  • Retry with a bigger budget
  • Exclude it and continue running

Q3A harness that absorbs unexpected exits into an excluded bucket:

  • Hides the bugs you could fix
  • Correctly separates artifacts from results
  • Is needed for any unattended run
  • Reduces the number of debugging cycles

Q4strict=True raising on the agent's own bad SQL is right during development because:

  • Bad SQL signals a prompt problem
  • SQL errors always corrupt the transaction
  • The agent cannot recover from errors
  • MySQL rejects the connection after errors

Q5In Mode B, committing versus rolling back at max_steps:

  • Never arises — you stopped to debug
  • Decides whether partial credit is given
  • Is required by transaction semantics here
  • Changes the measured restore mechanism latency

Where this leaves you

Every piece exists: scorer (40/40), mechanism with measured costs, guard (20/20, 0/40 blocked), trace, loop. Port them into src/dbagent/, pick max_steps, run it with strict=True, and fix whatever stops the process until nothing does.
