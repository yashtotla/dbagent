The loop is trivial; the boundaries are the experiment

Assembly session. Every decision is already made — this is where they compose, and where the last confounds are hiding.

The idea, in one analogy

Think about a database migration. The body is trivial SQL — a few ALTERs anyone could write. What breaks migrations is never the middle: it's whether you wrapped it in a transaction, what happens if it dies halfway, and whether you verified before or after.

An agent loop is the same shape. The loop is five lines and nobody gets it wrong. What decides your experiment is setup ordering, exit paths, and where you score — all of which sit outside the loop.

# this part is not where the difficulty is
for _ in range(max_steps):
    resp = client.messages.create(...)
    call = [b for b in resp.content if b.type == "tool_use"][0]
    result, done = dispatch(session, call.name, call.input, ...)
    if done: break

Six exit paths, and confounds in four of them

Two of these are decisions rather than mechanics, and both follow from things you've already established.

On max_steps: commit, don't roll back

The instinct is that uncommitted work is speculative and should be discarded. But in Mode A the agent's partial work is already committed — that is what Mode A means. Rolling back Mode B's would score the two arms under different rules: partial credit for A, zero for B.

So both modes score the state the agent actually produced when its budget ran out. (Scoring the uncommitted state on the same connection and then rolling back is equivalent — pick one, say which, and apply it to both arms.)

On end_turn: never spin

The model can return end_turn with no tool call — it stopped talking without doing anything. A loop that just re-requests will burn the entire step budget on nothing, and every one of those turns costs ~2 s and real tokens. Reprompt once with “call a tool or commit”, then terminate as incomplete.

Easy to miss because it never happens in testing and happens eventually in a 40-task run.

The prompts

Two system prompts, identical except for a paragraph describing the extra tools. That paragraph is the confound you agreed to state rather than net out:

# both modes
"Use execute_sql to inspect the table and to make modifications. Only SELECT,
 INSERT, UPDATE, DELETE, SHOW, DESCRIBE and EXPLAIN are permitted; DDL and
 transaction-control statements are rejected by the harness, so do not attempt
 them. When the table is in its final state, call commit_final_answer."

# Mode B only
"You may checkpoint before a risky modification and restore afterwards if the
 result is wrong. ... Restoring is cheap -- prefer trying an approach and undoing
 it over reasoning about which approach is correct."

Note the first block states the guard. That's deliberate: the dispatcher makes rejection impossible to bypass, and the prompt makes it rare. You want both — the guarantee and the lower rejection rate, since every rejection costs a turn.

The Mode B paragraph's last sentence is doing real work. “Prefer trying an approach and undoing it over reasoning about which approach is correct” is the behaviour you are testing for. Without it you'd likely measure an agent that has checkpoint tools and never uses them — and then you'd be measuring prompt design, not checkpointing.

Why a dry run matters more than usual here

Every exit path is exercised, the transaction statements are asserted, and it costs nothing. The alternative is discovering that end_turn spins — or that max_steps rolls back — on task 23 of a paid 40-task run.

Keep the scripted client. When you change the loop, this is your regression test.

Check yourself

Q1Where must CREATE TABLE run relative to START TRANSACTION?

  • Strictly before, since DDL commits
  • Immediately after, inside the transaction
  • Either works, order is irrelevant
  • After the first savepoint only

Q2The agent exhausts max_steps in Mode B. Rolling back its work would:

  • Penalize Mode B asymmetrically versus A
  • Match Mode A's behaviour exactly here
  • Have no effect on the score
  • Be required by transaction semantics here

Q3stop_reason is end_turn with no tool call. The loop should:

  • Not spin; terminate or reprompt once
  • Retry the same request until tools
  • Treat it as a successful completion
  • Score immediately and mark it passed

Q4Scoring before the commit requires the same connection because:

  • Uncommitted writes are invisible elsewhere
  • Row locks block other connections entirely
  • The savepoint stack is connection scoped
  • MySQL caches results per connection

Q5Which exit should be excluded from the comparison rather than scored?

  • Truncation at the token limit
  • Exhausting the configured step budget
  • The agent committing its answer
  • A statement the guard rejected

Ask your teacher

The most contestable thing here is the last line of the Mode B prompt: “prefer trying an approach and undoing it over reasoning about which approach is correct.” That is me telling the agent to explore. Without it you may measure an agent that has the tools and ignores them; with it, you have arguably prompted the result into existence. Neither choice is neutral, and whichever you pick belongs in the write-up as a stated design decision rather than buried in a prompt string. Argue it — I don't think there's a clean answer.
