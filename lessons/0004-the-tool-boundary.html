The tool boundary is your only enforcement point

You chose savepoint, which removed your fallback for agent-issued DDL. The tool dispatcher is now the only thing standing between the agent and silent corruption. One concept, one guard, one design rule.

The idea, in one analogy

You would never rely on a docstring to prevent SQL injection. Documentation describes what callers should send; validation decides what actually runs. Every engineer already knows this — the trick is noticing it applies to agents too.

System promptTool dispatcher
Analogous toDocumentationInput validation
ForceAdvisory — the model may ignore itMandatory — you decide what executes
Failure modeSilent non-complianceAn explicit, logged rejection

The agent cannot touch the database except through a tool call you dispatch. That makes the dispatcher the only place a correctness constraint can actually be enforced. Write “never issue DDL” in the system prompt and you have expressed a preference. Reject it at the tool boundary and you have built a guarantee.

This is Anthropic's own guidance, and it names your research question

From the agent-design docs: “Claude emits tool calls; your harness handles them. The shape of those tool calls determines what the harness can do.” On when to promote an action to a dedicated tool: “Reversibility is a useful criterion: hard-to-reverse actions … can be gated behind user confirmation.”

That is your project's thesis arriving from the other direction. The tool-design literature already treats irreversibility as the thing that decides where a boundary goes; you are measuring what happens when you make the action reversible instead. Worth a sentence in the write-up.

Allowlist, not blocklist

Now the guard itself. The obvious implementation is a blocklist — reject anything starting with CREATE, ALTER, DROP. It fails, and the way it fails is the lesson.

Consider what the agent sends and what each approach extracts:

Agent sendsVerb extractedBlocklistAllowlist
DROP TABLE tDROP reject ✓reject ✓
INSERT … VALUES ('DROP TABLE x')INSERT reject ✗ — substring match on a string literalallow ✓
/* harmless */ DROP TABLE t'' — nothing matches allow ✗ — fails OPENreject ✓ — fails CLOSED
The asymmetry that decides it

A comment prefix means the leading-keyword regex extracts nothing. Under a blocklist, “nothing” isn't on the forbidden list, so it passes — and MySQL executes the DROP (verified). Under an allowlist, “nothing” isn't on the permitted list either, so it's rejected.

Same input, same parse failure, opposite outcome. A blocklist requires you to enumerate every dangerous thing; an allowlist requires you to enumerate only what you need.

That should land personally. Two sessions ago you found the DDL guard yourself and stopped at DDL — when three of the four savepoint killers aren't DDL. An allowlist is the structural fix for exactly that failure mode: it doesn't ask you to think of everything.

Correction — DELETE

An earlier version of this lesson called DELETE a judgment call I'd made. Wrong, and Yash caught it. DBBench has three modification types. AgentBench's task.py branches on the literal tuple ("INSERT", "DELETE", "UPDATE") in two places — verified in source.

The dev split contains 20 INSERT, 20 UPDATE and zero DELETE. That is a property of this split, not of the benchmark, and the two are not interchangeable — I let the split's contents stand in for the benchmark's category definition. DELETE belongs in the allowlist on the same footing as the other two, and a scope sentence in the write-up should say “the dev split contains no DELETE tasks” rather than “DBBench modifications are INSERT and UPDATE.”

The tool

Tool definitions are just JSON Schema. Two things matter here — the description tells the model when to call it, and strict guarantees the input validates before you ever see it:

EXECUTE_SQL = {
    "name": "execute_sql",
    "description": (
        "Run one SQL statement against the task's table and return the result. "
        "Call this to inspect state or to make a modification. Only SELECT, INSERT, "
        "UPDATE, DELETE, SHOW, DESCRIBE and EXPLAIN are permitted — DDL and "
        "transaction-control statements are rejected by the harness."
    ),
    "strict": True,
    "input_schema": {
        "type": "object",
        "properties": {"sql": {"type": "string", "description": "A single SQL statement."}},
        "required": ["sql"],
        "additionalProperties": False,
    },
}

The dispatcher is where the guard lives — before execution, never after:

def dispatch(cur, name, args):
    if name == "execute_sql":
        reason = sql_guard.check(args["sql"])      # the enforcement point
        if reason:
            log(step, "rejected", args["sql"], reason)
            return reason                          # back to the agent, not fatal
        cur.execute(args["sql"])
        return format_rows(cur.fetchall())

Note what a rejection is: a tool result the agent reads and can act on, plus a trace event. Not a crash, not a silent drop. The agent gets to try something else, and you get a record that it reached for DDL — which is a finding about agent behaviour, not a harness failure.

“But the agent still needs to checkpoint”

It does — and the guard rejects SAVEPOINT, ROLLBACK and COMMIT. That is not withholding the capability. It is routing it through a typed interface instead of an opaque string — the same bash-versus-dedicated-tool distinction from the top of this lesson, applied one level in.

ToolMode AMode BWhat the harness actually issues
execute_sql(sql)✓✓guard, then execute
checkpoint()—✓SAVEPOINT sp_<depth>, returns the handle
restore(handle)—✓ROLLBACK TO SAVEPOINT sp_<handle>
commit_final_answer()✓✓COMMIT, end the task

Three things the harness can only do if it owns the statement:

  • Savepoint naming. Reusing a name replaces the old savepoint rather than nesting (Reference 01). An agent writing SAVEPOINT sp1 twice silently loses its outer branch. Depth-indexed names — sp_0, sp_1, … — have to be assigned by the harness.
  • Countable branches. Lesson 03 established that overhead scales with branches per turn. A checkpoint() call is one structured trace event; execute_sql("SAVEPOINT sp1") is a string you'd have to parse SQL out of.
  • Handle validation. restore(3) can be refused when depth 3 no longer exists, instead of surfacing as error 1305 mid-branch.

The two verbs the agent genuinely never needs: bare COMMIT happens once, through commit_final_answer; bare ROLLBACK would discard the entire task, and “reset to the start” is restore(0) against an sp_0 the harness takes immediately after START TRANSACTION.

That's the win

Identical agent behaviour. The only difference is a guard at the tool boundary, and it is the difference between a corrupted branch and a clean restore.

One thing that just invalidated a line in your spec

Check this before you write the experiment-hygiene section

CLAUDE.md lists your controls as “same model, same prompts, same task order, same max_steps, same temperature.” On current Claude models temperature, top_p and top_k are no longer accepted — passing them returns a 400. You cannot hold temperature fixed because you cannot set it at all.

The knobs that replace it are output_config={"effort": …} and the thinking setting, and those are what must be identical across Mode A and Mode B. Pin the exact model id and log it per run, as Reference 02 already says. Verify against the tool-use docs for whichever model you actually pin — do not take this from me.

Ask your teacher

The genuinely contestable claim left in this lesson is restore(handle) taking a handle at all. A flat restore() that always returns to the most recent checkpoint is simpler and matches how the agent probably thinks; an addressable handle allows jumping back several branches at once, which is a real tree search but also a much larger action space to reason about. I picked the handle because it makes branch structure legible in the trace — that is a measurement convenience, not evidence about what helps the agent. Argue it before you build it.
