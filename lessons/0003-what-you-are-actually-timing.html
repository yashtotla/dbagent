What you are actually timing

I benchmarked all four candidate mechanisms. The numbers are good for you. The first one I produced was also impossible — a checkpoint that cost less than nothing — and fixing it is most of the lesson.

Why this one

You have a working scorer and a mechanism shortlist. The remaining question is cost, and it is the one your write-up leans on hardest: your spec asks “what the overhead is,” and the reference paper's entire argument is that generic mechanisms are too slow. If your cost numbers are soft, the argument is soft.

Microbenchmarks at this scale are unusually easy to get wrong, because the thing you want to measure is smaller than the machinery you measure it with.

Before you read on — retrieval practice

You want the cost of ROLLBACK TO SAVEPOINT. You wrap it in time.perf_counter() and get 0.2 ms. From memory: name everything inside that 0.2 ms that is not InnoDB undoing rows.

Now compare

At least four: Python call overhead, the driver serialising the statement, the TCP round trip to the container, and MySQL parsing the SQL. On this machine those account for roughly half of the 0.2 ms. If you do not measure them separately you will report the network as if it were the storage engine.

The mistake I made first

To separate real work from overhead you measure a no-op and subtract. I used SELECT 1. That produced this:

SELECT 1  (round-trip floor)     p50   0.132 ms
SAVEPOINT sp1                    p50   0.105 ms   net  -0.027

A negative cost. Creating a checkpoint apparently took less time than doing nothing. When a measurement is impossible, the instrument is wrong — so I measured the two no-ops against each other:

Statementp50What the server sends back
SELECT 10.1220 msResult set — row data and column metadata
DO 10.1056 msOK packet only
SAVEPOINT sp10.1051 msOK packet only

SELECT 1 does more work than the thing it was supposed to baseline. It marshals a result set; SAVEPOINT does not. The floor was inflated by about 16%, so subtracting it understated everything — into negative territory for the cheapest operation. DO 1 evaluates an expression and returns an OK packet: same shape, correct floor.

This is the placebo mistake again, in miniature

Last session you rejected the placebo arm because it did not hold the agent's beliefs fixed — it changed the thing it claimed to control for. SELECT 1 fails the same test at the microbenchmark level: a baseline must do the same work as the treatment, minus only the one thing being isolated. Different scale, identical error. When a control looks neutral, ask what it is actually doing that the treatment is not.

Three things fall out

1 · Checkpointing is free; only restore costs anything. SAVEPOINT is indistinguishable from a bare round trip — it records a position in the undo log and nothing more. So the “checkpoint before every risky action” design has no steady-state cost. You pay only when you actually restore. That is a genuinely strong property and it is worth stating plainly.

2 · Replay-prefix is nearly flat in path length. Fitting the measured points: ≈ 6.4 ms + 0.15 ms × k. The fixed reset — drop database, create database, create table, re-insert 44 rows — dominates until k ≈ 42 statements. Your spec describes replay-prefix as “restore cost linear in path length”; at realistic agent path lengths it is effectively constant, and the constant is what matters. Worth correcting in your notes.

3 · docker commit at 510 ms reproduces the paper. Xu et al. report 0.416–6.915 s for Docker. You measured 510 ms at the bottom of that range, on a small container. Independent confirmation on your own hardware is worth a sentence — it is the one number in your write-up that says “I checked their claim rather than citing it.”

The claim you can actually make

The tempting headline is “savepoints are 2400× faster than container snapshots.” Do not write that. A savepoint rolls back rows in one table in one transaction. docker commit snapshots an entire container filesystem. CRIU snapshots process memory. Those cover wildly different amounts of state, and a ratio between them compares unlike units — the same category error you caught in the placebo arm.

The defensible claim is about coverage versus cost:

For the state a DBBench agent actually mutates, an engine-native primitive restores it for under a millisecond, while the generic mechanisms pay two to three orders of magnitude more to cover state the task never touches. The generality is real; here it is unused.

That is narrower, fully supported by the table, and much harder to attack.

The condition worth finding — where the paper's argument actually bites

The paper says generic mechanisms are “not fast enough” for agentic exploration. Your numbers let you say when that is true. Take an LLM tool-use turn at roughly 2 s — measure your own and substitute it, this is the one number here you should not take from me:

Mechanism1 branch / turn10 branches / turn
savepoint0.03%0.3%
replay-prefix0.5%5%
mysqldump5%53%
docker commit26%255% — 2.5× slowdown

At one branch per turn, even docker commit is a tax rather than a wall — the paper's claim is weak in that regime. It becomes decisive only under fine-grained branching, where an agent explores many candidates inside a single decision. So the paper's argument holds conditionally, and naming the condition is a contribution rather than a summary. It also tells you what your Mode B agent must actually do for any of this to matter: if it branches once per task, you will measure nothing.

State these limits

  • Localhost Docker. No network latency, no contention, no other tenants.
  • 44 rows, one table. Nothing here extrapolates to real data volumes.
  • docker commit at n=3 — enough to place the order of magnitude, not to characterise a distribution. Say n=3.
  • Savepoint requires holding a transaction open for the whole task. The manual warns that long transactions prevent undo-log purging; harmless at 44 rows, not harmless generally.
  • Restore latency is not the only cost. Lock retention and undo-log growth are real and unmeasured here.

Primary source

Read MySQL 8.0 Reference Manual §17.6.6, “Undo Logs” — short, and it explains why your numbers came out this way: rollback walks a per-transaction undo chain rather than copying data, which is exactly why cost tracked rows-dirtied (0.209 ms → 0.646 ms from 1 row to 44) and not table size. A mechanism whose cost scales with what you touched, rather than what exists, is the property the paper is asking for.
