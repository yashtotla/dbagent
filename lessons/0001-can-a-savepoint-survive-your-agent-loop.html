Can a savepoint survive your agent loop?

Your spec lists SAVEPOINT as the cheapest candidate for Mode B and flags its limits as “worth measuring rather than assuming.” This lesson settles one of them, by making a savepoint die in front of you.

Why this one first

Mode B needs a checkpoint mechanism, and you have four candidates. The choice is not a detail — it decides what your write-up can claim. If SAVEPOINT works, restore is a sub-millisecond undo-log walk and you have a genuinely sharp result to report against the seconds-scale generic mechanisms Xu et al. benchmarked. If it silently fails under your agent’s traffic, every Mode B number you produce is a measurement of a bug.

So: under what conditions does a savepoint survive an agent’s exploration branch? That is a small, answerable question, and answering it unblocks the design.

Before you read on — retrieval practice

From memory, no scrolling: list every event you think destroys an open savepoint in MySQL. Give yourself thirty seconds.

Now compare

There are four. Most people get the first and miss the rest. The one that will actually break your agent is #2 — and it fails silently.

The contract, in four lines

The whole of SAVEPOINT’s guarantee, quoted from the manual:

“All savepoints of the current transaction are deleted if you execute a COMMIT, or a ROLLBACK that does not name a savepoint.”

“Savepoints that were set at a later time than the named savepoint are deleted.”

“If the current transaction has a savepoint with the same name, the old savepoint is deleted and a new one is set.”

“Modifications that the current transaction made to rows after the savepoint was set are undone in the rollback, but InnoDB does not release the row locks…”

All four: MySQL 8.0 Reference Manual §15.3.4.

Notice what is not in that list: DDL. That omission is the trap, and it lives in a different chapter of the manual — which is exactly why people miss it.

The silent killer

DDL statements — CREATE TABLE, ALTER TABLE, DROP TABLE, CREATE INDEX, TRUNCATE TABLE — “implicitly end any transaction active in the current session, as if you had done a COMMIT before executing the statement.” No warning. No error. Your speculative write is now permanent, and the ROLLBACK that was supposed to undo it fails.

MySQL 8.0 Reference Manual §15.3.3

Watch it die

Docker is running on your machine but dbbench-mysql does not exist yet. Start it — this is your Milestone 0 container anyway:

docker run -d --name dbbench-mysql -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=pw mysql:8

# wait ~20s for first-time init, then check:
docker exec dbbench-mysql mysqladmin -uroot -ppw ping

Now run both branches. Identical, except branch A slips one DDL statement into the middle — exactly what an agent does when it decides an index would help:

docker exec -i dbbench-mysql mysql -uroot -ppw --force <<'SQL'
DROP DATABASE IF EXISTS lab; CREATE DATABASE lab; USE lab;
CREATE TABLE t (a TEXT); INSERT INTO t VALUES ('original');

SELECT '=== BRANCH A: agent issues DDL mid-branch ===' AS '';
START TRANSACTION;
SAVEPOINT sp1;
UPDATE t SET a = 'tentative';
CREATE INDEX idx ON t (a(10));       -- implicit COMMIT fires HERE
ROLLBACK TO SAVEPOINT sp1;
SELECT a AS after_rollback_A FROM t;

DROP DATABASE lab; CREATE DATABASE lab; USE lab;
CREATE TABLE t (a TEXT); INSERT INTO t VALUES ('original');

SELECT '=== BRANCH B: identical, no DDL ===' AS '';
START TRANSACTION;
SAVEPOINT sp1;
UPDATE t SET a = 'tentative';
ROLLBACK TO SAVEPOINT sp1;
SELECT a AS after_rollback_B FROM t;
SQL

Verified output — this is a real run, not an illustration. The error arrives on stderr, so it surfaces before the result rows rather than in sequence with them:

ERROR 1305 (42000) at line 9: SAVEPOINT sp1 does not exist

=== BRANCH A: agent issues DDL mid-branch ===
after_rollback_A
tentative          <- the speculative write COMMITTED. Unrecoverable.

=== BRANCH B: identical, no DDL ===
after_rollback_B
original           <- restored, sub-millisecond
Version note

The mysql:8 tag now resolves to 8.4.11, not 8.0 — worth pinning explicitly in your write-up’s methods section. Defaults confirmed on the running container: transaction_isolation = REPEATABLE-READ, autocommit = 1. The savepoint and implicit-commit semantics above are identical across 8.0 and 8.4; the manual links cite 8.0, and the behaviour was reproduced on 8.4.11.

The result

Branch A is Mode A behaviour occurring inside Mode B. The agent believed it was exploring safely; the harness reported no error until the rollback, by which point the write was already durable. An agent that hits this doesn’t just fail the task — it fails it while your logs claim checkpointing was enabled.

The research move

You now have a mechanism-level fact. Here is how it becomes a research-level one — which is what the second half of your mission is about.

Q3 is not trivia. “What other actors should observe while one agent is branching speculatively” is open challenge #1 in Xu et al. — they name it fork semantics and pose it as unresolved. MySQL has already picked an answer: conservative. Hide all tentative state, hold the row locks, make readers reconstruct the old version.

That reframes your write-up. Rather than “I added undo to an agent,” you can write: the generic mechanisms the paper benchmarks leave fork semantics undefined, whereas an engine-native primitive inherits a fully specified answer from the isolation level — for free, and three to six orders of magnitude faster. That is a claim with a mechanism behind it, and you can demonstrate the whole thing on a laptop.

It also sharpens the open question your spec deliberately left unresolved — plain two-mode comparison versus an argument about native forking. The evidence is starting to favour the second. Not yet decided; that is your call, and it should be made with numbers in hand.
