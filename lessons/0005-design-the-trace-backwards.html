Capture everything, derive narrowly

The first version of this lesson told you to derive your schema from the claims you expect to make. Yash rejected that, correctly. This is the rebuilt version, and it is a better lesson than the one it replaces.

What was wrong, precisely

The original conflated a sufficiency check with a capture policy. “For each claim, name the field” is a fine way to find what is missing. It then wrote that the resulting set “is usually smaller than log-everything, and unlike that pile, it is sufficient” — presenting minimality as a virtue.

Yash's objection: “We are assuming so much about the observations that we may or may not see.” That is exactly the failure mode. A trace built only from anticipated claims is structurally blind to the unanticipated finding — and on a project whose deliverable asks for named cases of behaviour nobody predicted, that blindness is fatal.

The asymmetry that settles it

Cost
Logging a field you turn out not to needbytes — 40 tasks × 2 modes × ~10 steps ≈ 800 records
Missing a field you turn out to needre-run the experiment — a day and a slice of API budget

There is no scale in this project at which curation pays for itself. Capture is cheap; irreversibility is expensive — which, you may notice, is the same asymmetry the whole project is about.

Two layers, two different rules

LayerRuleWhy
Raw captureLog everything cheap to observe. Append-only. Insurance against the question you haven't thought of yet
Derived viewCompute the agreed fields. Pure function of raw. Keeps analysis legible — and recomputable

The separation is what makes late questions survivable. Decide mid-analysis that you want “how many statements did the agent try before its first restore?” — under a two-layer design that is a new function over existing logs. Under a curated schema it is a re-run.

The original lesson already contained the germ of this and failed to follow it: it said “store events, derive counters” — then curated which events were allowed to exist. Yash's correction is that same rule applied one level up. The events are raw too.

So what is the backwards check for?

Not capture. Capture everything. The check tells you what must be decided or arranged before the run, because no amount of logging recovers it afterwards:

CommitmentWhy logging can't save you
mode labelNothing in an API response says “this was arm B”
scorer verdictpassed exists only if you run the scorer and write it down
held-fixed config“We held effort fixed” is unprovable unless effort is in the header
prompt identityA per-run hash, or you cannot show the prompt never drifted

Four design commitments. Everything else is capture — and the way to get capture right is not to think harder about it, but to stop deciding.

The field that proves the point

Here is what curation actually costs, from the demo below. Two runs of task_31:

task_31  A    passed=True   steps=1
task_31  B    passed=False  steps=1   truncated=True

Mode B hit stop_reason: "max_tokens" and stopped mid-task. Under the original schema — which logged no stop_reason — that reads as “Mode A recovered a task Mode B lost.” A fabricated finding, in the write-up's headline table, pointing the wrong direction.

And it is not random noise — it is directional

Mode B takes more steps → accumulates more tokens → is more likely to truncate. So the artifact systematically penalises the arm under study. That is a confound living inside the trace design, and nothing in the aggregate would have revealed it.

Three more in the same family, all cheap to capture and all previously dropped: usage (an entire cost axis), the assistant's content blocks (where “why did it restore?” actually lives), and the driver's verbatim db_error rather than a summarised reason string.

Two rules survive the rewrite, and one is new:

  • Store events, derive counters. Never write restores: 2 — count the events. A stored counter can disagree with what it summarises.
  • Flush every line. A run that dies at step 19 of 30 must leave 19 analysable lines. summarize() reports complete: false when the result record is missing, so a crash is visible rather than silently scored.
  • New — add fields freely. step(**observed) takes arbitrary keyword arguments and writes them through. Nothing downstream breaks when you add one, which is what makes “capture everything” a habit rather than an intention.

The quoted lines are the difference

The original narration showed what the agent did. This one shows why, in the agent's own words, because the assistant's text blocks are now captured. That paragraph is the deliverable — and it was unreachable under the curated schema, not because anyone decided to exclude reasoning, but because nobody listed it as a claim.

Synthetic data. No model was called. It shows the schema is sufficient, not a result.

Check yourself

Q1You log exactly (step, sql, response, latency). Which claim can you not make?

  • Which specific task checkpointing rescued
  • How long each statement took
  • What SQL the agent sent
  • How many steps were used

Q2“Cases where checkpointing enabled recovery” requires:

  • Paired per-task outcomes across modes
  • An aggregate pass rate difference
  • The median latency per mechanism
  • A count of total restores

Q3A Mode B run truncates at max_tokens and scores as failed. Without stop_reason you:

  • Record a harness artifact as evidence
  • Detect it from the low score
  • Recover it from the final hash
  • See it in the step count

Q4The right division between the raw log and the agreed fields is:

  • Capture everything, derive the agreed fields
  • Capture the agreed fields, derive nothing
  • Capture everything, store computed counters too
  • Capture selectively, derive whatever remains possible

Q5A field you chose not to log is:

  • A question you silently declined
  • A performance optimization worth making
  • Recoverable from the aggregate scores
  • Reconstructible from the final hash

What to do with it

Lift TraceWriter, summarize, compare_modes, check_controls and narrate from assets/trace.py into src/dbagent/. Note what compare_modes now does: it excludes truncated, refused and incomplete runs from the comparison and reports them separately, rather than scoring them.

Two habits worth keeping past this project:

  • Write the analysis before the run. If it executes end-to-end on synthetic data, the schema is sufficient. If it needs a field you didn't plan to log, you found out for free.
  • Then log more than the analysis needs anyway — because the analysis you wrote is, by construction, only the analysis you already thought of.

Ask your teacher

Open question the rewrite created: what belongs in the raw log that I still haven't thought of? That question has no closed-form answer, which is the point — but there is a cheap test. Take the three most surprising things an agent could plausibly do on these tasks (issue the same statement twice, restore without having checkpointed, commit with an empty table) and ask whether the current record would let you see it happen. Anything that fails that test is a field.
