Design the trace backwards

Your spec says failure analysis comes from reading traces, and that aggregates cannot answer “which cases did checkpointing rescue?” — both correct. It then specifies a field list that cannot answer it either.

The idea, in one analogy

You have built a table modelled on what the data is, then discovered it can't answer what the product actually asks. The fix is always the same: design the schema from the queries, not the entities.

A trace is that, with a worse feedback loop. Any field you don't log is a question you have silently declined to answer — and you find out which ones at analysis time, when re-running costs another day and another slice of API budget.

So: enumerate the sentences the write-up has to support. For each, ask what field makes it checkable. That set is your schema. It is usually smaller than “log everything useful,” and unlike that pile, it is sufficient.

Your spec's field list can't answer your spec's question

CLAUDE.md specifies logging (step, sql, response, latency). Hold it against the deliverable — “cases in which checkpointing enables recovery that linear execution cannot” — and the gaps are structural, not cosmetic:

MissingConsequence
modeYou cannot pair a task's two runs, so you cannot compute a discordant pair — the only kind that carries signal (Reference 02)
passedOutcome lives only in the scorer's memory. Recovery is undetectable from the trace.
event typeEvery record is assumed to be a SQL statement. A checkpoint, a restore and a rejection are none of them.
depthThe multi-level-backtracking limitation stays an admission instead of becoming a measured non-issue
two latenciesOne latency field cannot separate the ~0.9 ms database call from the ~2 s model call — which is the entire cost argument

The list isn't wrong so much as shaped for Mode A: a loop where every step is an execute_sql and nothing else exists. Mode B's whole vocabulary is missing. Same failure as the scorer in Lesson 02 — right in intent, short in the one dimension that mattered.

Backwards from the claims

Every sentence this project needs to support, and the field that makes it checkable:

Sentence you want to writeField it requires
“Mode B recovered tasks 7, 19 and 31; Mode A did not.”task_id, mode, passed
“In case 19 the agent tried X, saw the row count was wrong, restored, and tried Y.”ordered event records + rowcount
“Mode B explored 2.3 branches per task, Mode A 1.0.”checkpoint / restore events
“Multi-level backtracking never bound.”depth
“The guard forfeited no reachable score.”rejected events
“Mechanism cost was 0.01% of wall clock.”db_ms and llm_ms, separately
“Both modes had equal productive step budgets.”steps_used, rejections, per mode
“Model, effort and thinking were held fixed.”a run header

Notice what falls out: the last row is why there's a header record at all, and the db_ms/llm_ms split exists only because you settled last session that a step is an LLM call. Design decisions become schema fields. A trace written before those decisions were made would have merged both latencies and lost the argument.

The schema

Three record types in runs/<task_id>.<mode>.jsonl. Header, steps, result:

{"type":"run","task_id":"task_19","mode":"B","model":"claude-opus-5",
 "effort":"high","thinking":"adaptive","disable_parallel_tool_use":true,
 "max_steps":30,"guard":"allowlist-v1"}

{"type":"step","n":1,"event":"checkpoint","llm_ms":1950,"db_ms":0.10,"depth":1}
{"type":"step","n":2,"event":"execute_sql","llm_ms":2300,"db_ms":0.44,"depth":1,
 "sql":"UPDATE `Statistics` SET `Wins`='12' WHERE `Team`='Rams'","rowcount":3}
{"type":"step","n":4,"event":"restore","llm_ms":2400,"db_ms":0.66,"depth":1}
{"type":"step","n":5,"event":"rejected","llm_ms":1900,"depth":1,
 "sql":"CREATE INDEX ...","reason":"rejected: CREATE is not permitted"}

{"type":"result","task_id":"task_19","mode":"B","passed":true,"steps_used":7,
 "hash_got":"[('6e5be...',)]","hash_want":"[('6e5be...',)]"}
Two rules that are easy to get wrong

Store events, derive counters. Don't write a restores: 2 field — count restore events at analysis time. A stored counter can disagree with the events it summarises; a derived one cannot.

Flush every line. A run that dies at step 19 of 30 should still leave 19 analysable lines. Buffered writes turn a partial result into no result.

That last block is the deliverable

“Checkpointing enabled recovery in case 19: the agent's first UPDATE matched three rows instead of one, it inspected, restored, and re-ran with a narrower predicate.” That paragraph is generated from the trace, not reconstructed from memory — and no aggregate could have produced it.

The data is synthetic. No model was called. It exists to show the schema is sufficient, not to report a result.

Check yourself

Q1You log exactly (step, sql, response, latency). Which claim can you not make?

  • Which specific task checkpointing rescued
  • How long each statement took
  • What SQL the agent sent
  • How many steps were used

Q2“Cases where checkpointing enabled recovery” requires:

  • Paired per-task outcomes across modes
  • An aggregate pass rate difference
  • The median latency per mechanism
  • A count of total restores

Q3You omit depth. Which claim becomes unsupportable?

  • That multi-level backtracking never bound
  • That the guard blocked nothing
  • That restore stayed reliably submillisecond
  • That both modes shared prompts

Q4Designing a trace forward — logging whatever is convenient — produces:

  • Data you cannot analyze later
  • A minimal and sufficient record
  • Exactly the fields analysis needs
  • Smaller files and faster writes

Q5A field you chose not to log is:

  • A question you silently declined
  • A performance optimization worth making
  • Recoverable from the aggregate scores
  • Reconstructible from the final hash

What to do with it

Read assets/trace.py and lift TraceWriter, summarize and compare_modes into src/dbagent/. It is under 150 lines and the analysis functions are one per write-up sentence — compare_modes literally returns the deliverable's answer.

One habit worth keeping past this project: write the analysis script before the run. If it executes end-to-end against synthetic data, the schema is sufficient. If it needs a field you didn't plan to log, you have found that out for free instead of after burning the run.

Ask your teacher

The contestable choice here is one file per (task, mode) rather than one file per task with a mode field, or one file for the whole run. I picked it because a crashed or re-run mode doesn't corrupt the other arm, and because pairing is a filename join. But it makes “read one task's two runs side by side” a two-file operation, which is exactly what you'll be doing during failure analysis. Argue it before you write the writer.
