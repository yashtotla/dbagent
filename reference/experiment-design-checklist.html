Experiment Design Checklist

Run this before every measurement, not once at the start. All findings below were verified on this repo against MySQL 8.4.11 — none are hypothetical.

Gate 1 · Is the instrument calibrated?

Never measure an agent with an unverified scorer. Run the gold answers through the scorer first; if it cannot score a known-correct answer correctly, nothing downstream means anything.

Why there is no placebo here

The obvious control — Mode B's schema and prompt with no-op checkpoint() / restore() that report success — does not work, and an earlier version of this page was wrong to recommend it.

A placebo is valid when the belief being controlled for does not interact with the mechanism. Here belief drives policy: an agent told it can restore will rationally try a cheap guess first. Under a lying no-op it then proceeds from corrupted state. That arm is not “Mode A with a longer prompt” — it is a third condition, present in neither arm, and it can score below Mode A.

It also fails on its own terms: if the agent rarely explores, A′ ≈ A and the control is inert; if it explores often, A′ is actively sabotaged. Uninformative when safe, unsafe when informative. The decomposition B − A = [prompt] + [mechanism] is ill-posed, because the prompt's effect is conditional on the mechanism working.

What to do instead. Accept that Mode B is a system — prompt, tools and mechanism together — and say so. The comparison is between two agent designs, which is what the task asks for. Then make the policy change visible rather than netting it out:

  • Count branches per task in each mode — distinct candidate actions tried at a decision point. If B explores 2.3 and A explores 1.0, that is the policy change, quantified.
  • Count restores actually issued, and how many preceded a task that went on to pass. This is what produces the named recovery cases the deliverable asks for.
  • If time allows, vary cost not truthfulness — savepoint vs replay-prefix. Both restore correctly, so the agent's plan stays valid and only mechanism cost differs. That is a clean control, and it is the comparison the reference paper is about.

A′ is still worth building as a separate experiment: it models the lesson-01 DDL bug and answers “what does an agent do when its checkpoint silently fails?” Just do not call it a control.

Gate 3 · Can the number carry the claim?

The design is paired — both modes run the same 40 tasks — so only discordant tasks carry information. Exact paired (McNemar) test:

Threshold: about six clean flips in one direction. Below that, say so, and shift the write-up's weight onto the mechanism argument and the cost measurements — neither depends on N.

Gate 4 · Are the limits stated?

Write these down before a reviewer asks. Naming limits is evidence you understand the result.

  • 40 tasks · one benchmark · one model · one schema shape
  • Single table, all columns TEXT, 12–44 rows
  • No multi-table transactions, no concurrency, no large data
  • Single-connection agent; nothing here speaks to what other observers see (the paper's open challenge #1)
  • Named recovery cases matter more than aggregates — cite specific task ids from runs/<task_id>.jsonl, not just totals
