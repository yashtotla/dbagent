Trace Schema

Derived backwards from the sentences the write-up must support. Any field not here is a question you have declined to answer.

1 · Claims → fields

SentenceRequired field
“Mode B recovered tasks 7, 19, 31; Mode A did not.”task_id, mode, passed
“The agent tried X, saw the row count, restored, tried Y.”ordered event + rowcount
“B explored 2.3 branches/task, A explored 1.0.”checkpoint / restore events
“Multi-level backtracking never bound.”depth
“The guard forfeited no reachable score.”rejected events
“Mechanism cost was 0.01% of wall clock.”db_ms and llm_ms, separate
“Both modes had equal productive step budgets.”steps_used, rejections, per mode
“Model, effort, thinking held fixed.”run header
What CLAUDE.md specifies is insufficient

(step, sql, response, latency) is shaped for a Mode A loop where every step is an execute_sql. It carries no mode (so runs can't be paired), no passed (so recovery is undetectable), no event type (so checkpoint, restore and rejection are inexpressible), no depth, and one merged latency where the whole cost argument needs two.

2 · The records

One file per (task, mode): runs/<task_id>.<mode>.jsonl.

// header — one per file, first line
{"type":"run","task_id":"task_19","mode":"B","model":"claude-opus-5",
 "effort":"high","thinking":"adaptive","disable_parallel_tool_use":true,
 "max_steps":30,"guard":"allowlist-v1"}

// steps — one per LLM call. event ∈ execute_sql | rejected |
//         checkpoint | restore | commit_final_answer
{"type":"step","n":1,"event":"checkpoint","llm_ms":1950,"db_ms":0.10,"depth":1}
{"type":"step","n":2,"event":"execute_sql","llm_ms":2300,"db_ms":0.44,"depth":1,
 "sql":"UPDATE ...","rowcount":3}
{"type":"step","n":4,"event":"restore","llm_ms":2400,"db_ms":0.66,"depth":1}
{"type":"step","n":5,"event":"rejected","llm_ms":1900,"depth":1,
 "sql":"CREATE INDEX ...","reason":"rejected: CREATE is not permitted"}

// result — one per file, last line
{"type":"result","task_id":"task_19","mode":"B","passed":true,"steps_used":7,
 "hash_got":"[('6e5be...',)]","hash_want":"[('6e5be...',)]"}

3 · Rules

  1. Store events, derive counters. Never write restores: 2 — count restore events at analysis time. A stored counter can disagree with the events it summarises.
  2. Flush every line. A run that dies at step 19 of 30 must still leave 19 analysable lines.
  3. One step = one LLM call. With disable_parallel_tool_use set, that is also one tool call and one DB statement — see Reference 05.
  4. Two latencies, always separate. db_ms is ~0.9 ms, llm_ms is ~2 s. Merging them destroys the cost argument (Reference 03).
  5. Header carries the controls. Model id, effort, thinking, parallel-tool-use, max_steps, guard version. These are the Reference 02 hold-fixed list; logging them per run is how you prove they were held.

4 · Analysis — one function per claim

FunctionAnswers
summarize(records)Per-run counters: steps, checkpoints, restores, rejections, max depth, both latencies
compare_modes(summaries)The deliverable — which task ids B recovered, which A won, how many discordant pairs
narrate(records)One task's branch structure as readable lines — the named-case paragraph

Implementation: assets/trace.py. The discordant count from compare_modes feeds straight into the exact paired test in Reference 02 — six clean flips in one direction is the reportable threshold.

5 · The habit

Write the analysis script before the run. If it executes end-to-end against synthetic data, the schema is sufficient. If it needs a field you didn't plan to log, you found out for free rather than after burning a day of API budget.
