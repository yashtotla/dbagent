Trace Schema

Capture everything cheap to observe; derive the agreed fields from it. The raw log is insurance against the question you haven't thought of yet.

1 · Two layers, two rules

LayerRuleWhy
Raw captureLog everything cheap to observe. Append-only. An extra field costs bytes; a missing one costs a re-run
Derived viewPure function of raw. Recompute freely. A late question becomes a new function, not a new run

At 40 tasks × 2 modes × ~10 steps ≈ 800 records, there is no scale at which curation pays for itself. Capture is cheap; irreversibility is expensive — the same asymmetry the project is about.

2 · The four things logging cannot save you from

Enumerating your claims does not tell you what to capture. It tells you what must be decided or arranged in advance:

CommitmentWhy it is unrecoverable afterwards
mode labelNothing in an API response says “this was arm B”
scorer verdictpassed exists only if you run the scorer and record it
held-fixed config“Effort was held fixed” is unprovable unless effort is in the header
prompt identitysystem_sha / tools_sha per run, or drift is undetectable

3 · Fields that are easy to skip and expensive to lack

FieldWhat it prevents
stop_reason Scoring a harness artifact as a result. A run truncated at max_tokens looks identical to a wrong answer — and Mode B takes more steps, so it truncates more often. The artifact is directional, penalising the arm under study.
usageLosing the cost axis entirely
content blocksLosing the agent's stated reasoning — where “why did it restore?” lives
db_error verbatimSummarising an error into a reason string discards the driver's own message
tsWall-clock ordering across files; durations alone can't reconstruct it
result record presentA crashed run silently scoring as a failure (complete: false)

4 · The records

runs/<task_id>.<mode>.jsonl — header, steps, result.

{"type":"run","task_id":"task_19","mode":"B","system_sha":"a1b2c3d4e5f6",
 "tools_sha":"9f8e7d6c5b4a","system":"...","tools":[...],
 "model":"claude-opus-5","effort":"high","thinking":"adaptive",
 "disable_parallel_tool_use":true,"max_steps":30,"guard":"allowlist-v1"}

{"type":"step","n":3,"ts":1786...,"event":"execute_sql",
 "llm_ms":2050,"db_ms":0.28,"depth":1,"stop_reason":"tool_use",
 "usage":{"input_tokens":3610,"output_tokens":66,"cache_read_input_tokens":0},
 "content":[{"type":"text","text":"Three rows changed — I expected one."},
            {"type":"tool_use","name":"execute_sql"}],
 "sql":"SELECT * FROM `Statistics` WHERE `Team`='Rams'","rowcount":3,

{"type":"result","task_id":"task_19","mode":"B","passed":true,"steps_used":7,
 "error":null,"hash_got":"[('6e5be...',)]","hash_want":"[('6e5be...',)]"}

event ∈ execute_sql | rejected | checkpoint | restore | commit_final_answer. One step = one LLM call, given disable_parallel_tool_use (Reference 05).

5 · Rules

  1. Store events, derive counters. Never write restores: 2 — count the events, every time.
  2. Flush every line. A run that dies at step 19 of 30 must leave 19 analysable lines.
  3. Add fields freely. The writer takes arbitrary keyword arguments and passes them through, so nothing downstream breaks when you capture one more thing.
  4. Two latencies, never merged. db_ms ≈ 0.9 ms, llm_ms ≈ 2 s (Reference 03).
  5. Never log secrets. The header captures the system prompt and tool schemas — keep credentials out of both.

6 · Analysis

FunctionAnswers
summarize()Per-run counters, plus truncated, refused, complete, token totals
compare_modes()The deliverable — which tasks B recovered, plus the runs excluded as harness artifacts rather than scored
check_controls()Whether system_sha/tools_sha stayed stable within each mode
narrate()One task's branch structure with the agent's own words — the named-case paragraph

The discordant count from compare_modes() feeds the exact paired test in Reference 02 — six clean flips one way is the reportable threshold. Report the excluded-artifact list alongside it; a silent exclusion is the same failure as a silent inclusion.

7 · The habits

  1. Write the analysis before the run. If it runs end-to-end on synthetic data, the schema is sufficient.
  2. Then log more than it needs — the analysis you wrote covers only what you already thought of.
  3. Surprise test. Name three odd things the agent could plausibly do (repeat a statement, restore without checkpointing, commit an empty table). If the record wouldn't let you see it happen, that's a missing field.
