Task Lifecycle

The implementation checklist for one task. The loop is trivial; everything that decides the experiment is at a boundary.

1 · Ordering

#StepForced by
1DROP/CREATE DATABASE; CREATE TABLE (all TEXT, backticked); INSERT rows DDL implicitly commits — must precede START TRANSACTION (Ref 01)
2Mode B: START TRANSACTION; SAVEPOINT sp_0 sp_0 is the restore floor — “reset to start” without a bare ROLLBACK (Ref 05)
3the agent loop—
4commit, then score on the same connection A reconnecting scorer reads pre-branch state (Ref 01)
5DROP DATABASENext task starts clean

Mode A has no explicit transaction: autocommit is on and every statement commits as it runs. That asymmetry is the variable under study.

2 · Three outcomes

#OutcomeWhat happens
1commit_final_answerHash the table, compare, record
2anything unexpectedRaise. Stop the process, read the trace, fix
3max_steps without committingRaise. Stop, read the trace

No fourth bucket, no excluded-artifact set, no partial credit. Every non-happy path during development is a bug you can still fix, and a harness that keeps going is a harness that hides them.

Two postures — only one is designable now

Debugging (now): crash loudly on anything but tool_use. Measurement (later): tolerate whatever survived fixing. You cannot design the second first, because you don't yet know which failures are irreducible.

strict=True (default) also raises on the agent's own SQL errors — broken SQL usually means the prompt or tool description is wrong. Flip to strict=False once the run is clean, and bad SQL becomes an ordinary tool result the agent reacts to.

There is no “scoring an incomplete task”

The scorer is one SELECT hashing rows. It does not know an agent exists, whether it finished, or how many turns it took. So the only question is what is on the table when we hash it — and on outcomes 2 and 3 you never get there, because you stopped to look.

3 · Request shape

client.messages.create(
    model="claude-opus-5",            # pin exactly; log it in the header
    max_tokens=8192,
    system=system_for(mode),
    tools=tools_for(mode),
    tool_choice={"type": "auto", "disable_parallel_tool_use": True},
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    messages=messages,
)

Hold identical across modes: model id, effort, thinking, max_tokens, max_steps, the guard, and disable_parallel_tool_use. Not temperature — it is no longer accepted (Ref 05).

4 · The prompts

Identical except one paragraph. That paragraph is the confound — state it, don't net it out.

BlockModesDoing what
Task framing + execute_sql usageA, BBaseline
Guard contents (“DDL and transaction-control are rejected”)A, BLowers the rejection rate; the dispatcher still guarantees it
Checkpoint/restore descriptionBThe confound. Extra tools ⇒ longer prompt ⇒ different action space
“Prefer trying and undoing over reasoning about which is correct”BContested. Without it you may measure an agent that ignores its tools; with it you have prompted the behaviour. State whichever you choose.

5 · Pre-flight

  1. uv run python assets/milestone0.py → 40/40. If not, stop.
  2. uv run python assets/sql_guard.py → 20/20, 0/40 gold labels blocked.
  3. uv run python assets/agent_loop.py → all three outcomes, no API calls.
  4. uv run python assets/trace.py → analysis runs end-to-end on synthetic data.
  5. Pick max_steps: size it for Mode B (~10 turns for a 3-alternative exploration), use the same number in Mode A, and report turns actually used — that comparison is the policy-change measurement.
  6. Run with strict=True and fix whatever stops the process until nothing does.
  7. Confirm check_controls() reports stable per mode after the run.
