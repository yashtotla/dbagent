MySQL Transaction Boundaries

What a savepoint promises, what silently destroys it, and who can see a speculative branch. Every claim here is quoted from the MySQL 8.0 manual — check the citation before you trust me.

1 · The savepoint contract

Four normative statements from the manual. These are the whole surface.

RuleManual wording (verbatim)
COMMIT or bare ROLLBACK wipes every savepoint “All savepoints of the current transaction are deleted if you execute a COMMIT, or a ROLLBACK that does not name a savepoint.”
Reusing a name replaces, it does not nest “If the current transaction has a savepoint with the same name, the old savepoint is deleted and a new one is set.”
Rolling back to a savepoint deletes newer ones “Savepoints that were set at a later time than the named savepoint are deleted.”
Rollback undoes rows but keeps locks “Modifications that the current transaction made to rows after the savepoint was set are undone in the rollback, but InnoDB does not release the row locks that were stored in memory after the savepoint.”

Missing savepoint raises ERROR 1305 (42000): SAVEPOINT identifier does not exist.

Source: MySQL 8.0 Reference Manual §15.3.4 — SAVEPOINT, ROLLBACK TO SAVEPOINT, and RELEASE SAVEPOINT

2 · The four ways a savepoint dies

Only the first is obvious. The other three are what will actually bite an agent loop.

#CauseWarning you getReachable in dbagent?
1Explicit COMMIT / bare ROLLBACK None — intendedYes, harness-controlled
2Implicit commit from DDL — CREATE TABLE, ALTER TABLE, DROP TABLE, CREATE INDEX, TRUNCATE TABLE None. Silent. Yes — agent can emit DDL at will
3Session ends or reconnects Transaction rolls back wholesale Yes — any pymysql reconnect
4BEGIN / START TRANSACTION / SET autocommit=1 / LOCK TABLES None — these implicitly commit first Yes, if the agent issues them
The one that matters

Cause #2 is the trap. DDL commits the open transaction before it runs, so a speculative UPDATE made earlier in the branch becomes permanent — and the subsequent ROLLBACK TO SAVEPOINT fails with error 1305. The agent believes it is exploring safely and is not. This is Mode A behaviour leaking into Mode B.

TEMPORARY tables are the exception: “CREATE TABLE and DROP TABLE statements do not commit a transaction if the TEMPORARY keyword is used.”

Source: MySQL 8.0 Reference Manual §15.3.3 — Statements That Cause an Implicit Commit

3 · Who sees a speculative branch

Under InnoDB’s default REPEATABLE READ, uncommitted branch state is private to the writing session. Multi-versioning is what makes this true: each row carries a DB_TRX_ID (last transaction to touch it) and a DB_ROLL_PTR roll pointer into the undo log, so a reader can reconstruct the pre-branch version rather than block on it.

ObserverPlain SELECTWrite to same rows
The branching sessionIts own tentative writesProceeds
Another connectionPre-branch state (undo-log reconstruction) Blocks — row locks are held
The scorer, if it reconnectsPre-branch state — wrong answer—
Why this is the research question, not a detail

“What other actors should observe while one agent is branching speculatively” is open challenge #1 in Xu et al. — they call it fork semantics. MySQL already answers it one way (conservative: hide everything, hold locks). Naming that as a design point rather than an implementation accident is the difference between a lab report and a research note.

Source: MySQL 8.0 Reference Manual §17.3 — InnoDB Multi-Versioning

5 · Derived rules for this project

  1. Create the table before opening the transaction. Per-task CREATE TABLE is DDL; run it, then START TRANSACTION, then hand control to the agent.
  2. Treat agent-issued DDL as a branch-abort event. Either reject it at the tool boundary or detect it and fall back to a coarser restore mechanism. Silently losing the savepoint is the one outcome you cannot allow.
  3. Score on the same connection that wrote. A reconnecting scorer reads pre-branch state and reports a false negative.
  4. One connection per task, held open. Savepoints are session-scoped; a pool that hands out a different connection mid-task destroys the branch.
  5. Never reuse a savepoint name for a nested branch — it replaces the outer one instead of nesting. Use a depth-indexed name: sp_0, sp_1, …
