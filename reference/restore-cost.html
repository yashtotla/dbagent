Restore Cost, measured

Every number below was measured on this machine, not cited. Reproduce with uv run python assets/bench_restore.py.

Conditions

MySQL 8.4.11 in Docker on localhost · table game_results, 44 rows × 5 columns (the largest of the 40 modification tasks) · warmed up before timing · median of n reported · floor measured with DO 1.

Replay-prefix fit: ≈ 6.4 ms + 0.15 ms × k. The fixed reset dominates until k ≈ 42, so at realistic path lengths the cost is effectively constant — not “linear in path length” as it is usually described.

Measurement rules that produced these

  1. The floor must match the treatment's shape. SELECT 1 returns a result set; SAVEPOINT returns an OK packet. Using the former as a floor inflates it ~16% and drives cheap operations negative. Use DO 1.
  2. Time only the operation. Setup — the SAVEPOINT, the dirtying UPDATE — belongs outside the timed region.
  3. Warm up. First calls pay for connection state and page cache.
  4. Report p50 and p95, never the mean. p95 is 2.2× p50 for the 1-row rollback; a mean would hide that.
  5. Do not out-claim your resolution. Run-to-run drift here is ≈0.015 ms. Anything smaller is “below measurement resolution,” not a number.
  6. Report small n as small n. docker commit at n=3 places an order of magnitude; it does not characterise a distribution.

Against the published numbers

Xu et al. report 0.416–6.915 s for Docker. The 510 ms measured here sits at the bottom of that range — independent confirmation on different hardware, worth one sentence in the write-up.

Correction to Reference 01

An earlier version of Reference 01 claimed savepoint rollback is “three to six orders of magnitude” below the paper's mechanisms. Measured, the correct range is two to six: against CRIU's best case (0.060 s) a 44-row rollback is ~93× — two orders, not three. The six-order end holds only against the AWS VM snapshot (353 s). Fixed in place.

Coverage, not speed

Do not write “savepoints are 2440× faster.” The mechanisms restore different amounts of state:

MechanismRestoresMisses
ROLLBACK TO SAVEPOINTRows in one transaction DDL, filesystem, process memory, anything outside the session
replay-prefixWhole database from initFilesystem, process memory
mysqldumpWhole database, logicallyProcess memory, container state
docker commitContainer filesystemProcess memory (needs CRIU)

The defensible claim:

For the state a DBBench agent actually mutates, an engine-native primitive restores it for under a millisecond, while generic mechanisms pay two to three orders of magnitude more to cover state the task never touches. The generality is real; here it is unused.

When the paper's argument bites

Restore overhead as a fraction of one LLM tool-use turn. Turn latency assumed at 2 s — measure your own and substitute it.

Mechanism1 branch / turn10 branches / turn
savepoint0.03%0.3%
replay-prefix0.5%5%
mysqldump5%53%
docker commit26%255% — 2.5× slowdown

Overhead scales with branches, not tasks. At one branch per turn the generic mechanisms are a tax; only fine-grained branching makes them a wall. The paper's claim therefore holds conditionally, and naming the condition is a contribution rather than a summary.

Limits to state

  • Localhost Docker — no network latency, no contention, no other tenants
  • 44 rows, one table; nothing extrapolates to real data volumes
  • docker commit at n=3
  • Savepoint needs a transaction held open all task; long transactions block undo-log purging
  • Lock retention and undo-log growth are real costs, unmeasured here
