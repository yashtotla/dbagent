The Tool Boundary

The dispatcher is the only place a correctness constraint can be enforced. This is the implementation-section material for the write-up.

1 · The rule

The agent reaches the database only through a tool call you dispatch. Therefore:

System promptTool dispatcher
Analogous toDocumentationInput validation
ForceAdvisory — may be ignoredMandatory — you decide what runs
Use forReducing how often the guard firesGuaranteeing it never doesn't

Write the constraint in both places. The prompt lowers the rejection rate; the dispatcher makes the rejection rate irrelevant to correctness.

2 · Allowlist, never blocklist

InputVerb extractedBlocklistAllowlist
DROP TABLE tDROPreject ✓reject ✓
INSERT … VALUES ('DROP TABLE x')INSERT reject ✗ false positiveallow ✓
/* c */ DROP TABLE t'' allow ✗ fails openreject ✓ fails closed

A blocklist requires enumerating every dangerous statement — miss one and it fails open. An allowlist requires enumerating only what the task needs, and refuses anything it cannot positively identify.

ALLOWED = {"SELECT", "INSERT", "UPDATE", "DELETE",
           "SHOW", "DESCRIBE", "DESC", "EXPLAIN"}

Strip comments before extracting the verb. Without it, /* c */ DROP TABLE t yields no keyword at all.

Verified free: 0/40 gold label statements are blocked; all 40 are single statements.

Three modification types, two in this split

DBBench's modification family is INSERT / UPDATE / DELETE — AgentBench's task.py branches on the literal tuple ("INSERT", "DELETE", "UPDATE") in two places (verified in source).

The dev split contains 20 INSERT, 20 UPDATE, and zero DELETE. Don't let the split's contents stand in for the benchmark's definition: DELETE belongs in the allowlist on the same footing as the other two, and the write-up's scope sentence should read “the dev split contains no DELETE tasks,” not “DBBench modifications are INSERT and UPDATE.”

3 · What the guard rejects, and why

CategoryExamplesWhy it must be rejected
DDLCREATE, ALTER, DROP, TRUNCATE, RENAME Implicit commit destroys the savepoint silently
Transaction controlCOMMIT, ROLLBACK, BEGIN, START TRANSACTION, SAVEPOINT, RELEASE Deletes savepoints directly, or implicitly commits first. The harness owns these.
Session stateSET, LOCK, UNLOCK, USE SET autocommit=1 and LOCK TABLES implicitly commit
Unparseableempty input, comment-only Fails closed by construction

Free second layer: pymysql rejects multi-statement payloads by default — UPDATE t SET a='x'; DROP TABLE t raises ProgrammingError (1064). Verified, but verify it yourself rather than assuming: it disappears the moment anyone passes CLIENT.MULTI_STATEMENTS.

4 · Rejected ≠ withheld — the Mode B tool surface

The agent still needs to checkpoint and restore. It reaches those through dedicated tools, not raw SQL — the bash-versus-dedicated-tool distinction applied one level in.

ToolMode AMode BHarness issues
execute_sql(sql)✓✓guard, then execute
checkpoint()—✓SAVEPOINT sp_<depth> → handle
restore()—✓ROLLBACK TO SAVEPOINT sp_<top>, keeps it
commit_final_answer()✓✓COMMIT, end task

What owning the statement buys:

  • Naming. A reused savepoint name replaces rather than nests (Reference 01) — an agent writing SAVEPOINT sp1 twice silently loses its outer branch. Depth-indexed names must come from the harness.
  • Countable branches. One structured trace event per checkpoint, versus parsing SQL out of strings. Reference 03 shows overhead scales with branches per turn — you can only report that if branching is legible.
  • Depth tracking. Refuse a restore() below depth 0 instead of issuing a bare ROLLBACK that would discard the whole task.
MVP scope — flat restore(), and why that's defensible

restore() takes no argument: it rolls back to the most recent checkpoint and keeps that savepoint. Deferred to a later extension: multi-level backtracking — going up past the most recent checkpoint, reachable either by pop-semantics or an addressable handle.

Verified on MySQL 8.4.11, and this is the justification to use:

  • Repeated flat restores across nested savepoints walk the stack — L3 → L2 → L1 → original. Flat restore reaches any ancestor; the handle only saves calls.
  • One savepoint survives repeated rollbacks — try A → restore → try B → restore → try C, all returning 'original'. The N-alternatives-at-one-decision-point pattern needs one checkpoint and zero handles.

So the cut removes convenience, not reachability. Say that in the write-up rather than “it was hard to reason about” — the first is accepted, the second is discounted.

Then close it with a measurement: log checkpoint depth per task. If the agent never exceeds depth 1 across all 40 tasks, multi-level backtracking was never reachable and the simplification forfeited nothing. One integer turns an admitted gap into a measured non-issue.

Never needed by the agent: bare COMMIT (happens once, via commit_final_answer) and bare ROLLBACK (discards the whole task — “reset to start” is restore(0) against an sp_0 taken immediately after START TRANSACTION).

Disable parallel tool use

Parallel tool use is on by default — one assistant message may carry several tool_use blocks, which the harness is expected to execute concurrently and return as one batch. That is incoherent here: checkpoint, execute_sql and restore mutate a single open transaction in sequence, on a single connection, and blocks in one message carry no ordering guarantee. Running restore concurrently with the UPDATE it should undo is not well-defined.

tool_choice={"type": "auto", "disable_parallel_tool_use": True}

With this set, one LLM call = one tool call = one DB statement. A “step” is then unambiguous, and it is the expensive unit (~2 s) rather than the cheap one (~0.9 ms). Budget and report steps in LLM calls; never cap database operations, which are four orders of magnitude cheaper.

It must be set identically in both modes — see Reference 02.

Confound note: Mode B has two extra tools, so its prompt and action space differ from Mode A's. That is unavoidable by construction — state it and measure the policy change rather than trying to net it out. A rejected statement also consumes a turn, so if Mode B fumbles into rejections more often it has a smaller productive budget; log rejections per mode and report both counts.

5 · The rejection protocol

  1. Return the reason to the agent as a tool result. It can then try something else — a rejection costs a step, not the task.
  2. Log it to runs/<task_id>.jsonl. An agent reaching for DDL is a finding about agent behaviour, not a harness failure.
  3. Never abort the task, and never drop silently — silence is the exact failure mode the project exists to study.
  4. Identical guard in both modes. Guarding only Mode B changes two variables at once. See Reference 02.

6 · Tool definition shape

{
  "name": "execute_sql",
  "description": "Run one SQL statement … Only SELECT, INSERT, UPDATE, DELETE, "
                 "SHOW, DESCRIBE and EXPLAIN are permitted — DDL and transaction-"
                 "control statements are rejected by the harness.",
  "strict": True,
  "input_schema": {
    "type": "object",
    "properties": {"sql": {"type": "string", "description": "A single SQL statement."}},
    "required": ["sql"],
    "additionalProperties": False,
  },
}
  • Be prescriptive about when to call it, not just what it does. The trigger condition belongs in the tool's own description, not only the system prompt.
  • strict: True guarantees the input validates against the schema. It requires additionalProperties: False and an explicit required list.
  • State the guard in the description too — the agent then avoids the rejection rather than discovering it.
Correction to CLAUDE.md § Experiment hygiene

The controls list says “same temperature.” On current Claude models temperature, top_p and top_k are no longer accepted — passing them returns a 400. Temperature cannot be held fixed because it cannot be set.

The replacements are output_config={"effort": …} and the thinking setting; those are what must be identical across modes. Pin the exact model id and log it per run. Verify against the current tool-use docs for whichever model you pin.

7 · Why this is a research point, not plumbing

Anthropic's own agent-design guidance says a bash tool gives the harness only an opaque command string, whereas promoting an action to a dedicated tool gives it “an action-specific hook with typed arguments it can intercept, gate, render, or audit” — and names the criterion for doing so:

“Reversibility is a useful criterion: hard-to-reverse actions … can be gated behind user confirmation.”

The tool-design literature already treats irreversibility as what decides where a boundary goes. This project measures what changes when the action becomes reversible instead — the same idea approached from the other side. That connection belongs in the write-up.
