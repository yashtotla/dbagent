The Tool Boundary

The dispatcher is the only place a correctness constraint can be enforced. This is the implementation-section material for the write-up.

1 · The rule

The agent reaches the database only through a tool call you dispatch. Therefore:

System promptTool dispatcher
Analogous toDocumentationInput validation
ForceAdvisory — may be ignoredMandatory — you decide what runs
Use forReducing how often the guard firesGuaranteeing it never doesn't

Write the constraint in both places. The prompt lowers the rejection rate; the dispatcher makes the rejection rate irrelevant to correctness.

2 · Allowlist, never blocklist

InputVerb extractedBlocklistAllowlist
DROP TABLE tDROPreject ✓reject ✓
INSERT … VALUES ('DROP TABLE x')INSERT reject ✗ false positiveallow ✓
/* c */ DROP TABLE t'' allow ✗ fails openreject ✓ fails closed

A blocklist requires enumerating every dangerous statement — miss one and it fails open. An allowlist requires enumerating only what the task needs, and refuses anything it cannot positively identify.

ALLOWED = {"SELECT", "INSERT", "UPDATE", "DELETE",
           "SHOW", "DESCRIBE", "DESC", "EXPLAIN"}

Strip comments before extracting the verb. Without it, /* c */ DROP TABLE t yields no keyword at all.

Verified free: 0/40 gold label statements are blocked. All 40 are single statements, 20 INSERT and 20 UPDATE.

3 · What the guard rejects, and why

CategoryExamplesWhy it must be rejected
DDLCREATE, ALTER, DROP, TRUNCATE, RENAME Implicit commit destroys the savepoint silently
Transaction controlCOMMIT, ROLLBACK, BEGIN, START TRANSACTION, SAVEPOINT, RELEASE Deletes savepoints directly, or implicitly commits first. The harness owns these.
Session stateSET, LOCK, UNLOCK, USE SET autocommit=1 and LOCK TABLES implicitly commit
Unparseableempty input, comment-only Fails closed by construction

Free second layer: pymysql rejects multi-statement payloads by default — UPDATE t SET a='x'; DROP TABLE t raises ProgrammingError (1064). Verified, but verify it yourself rather than assuming: it disappears the moment anyone passes CLIENT.MULTI_STATEMENTS.

4 · The rejection protocol

  1. Return the reason to the agent as a tool result. It can then try something else — a rejection costs a step, not the task.
  2. Log it to runs/<task_id>.jsonl. An agent reaching for DDL is a finding about agent behaviour, not a harness failure.
  3. Never abort the task, and never drop silently — silence is the exact failure mode the project exists to study.
  4. Identical guard in both modes. Guarding only Mode B changes two variables at once. See Reference 02.

5 · Tool definition shape

{
  "name": "execute_sql",
  "description": "Run one SQL statement … Only SELECT, INSERT, UPDATE, DELETE, "
                 "SHOW, DESCRIBE and EXPLAIN are permitted — DDL and transaction-"
                 "control statements are rejected by the harness.",
  "strict": True,
  "input_schema": {
    "type": "object",
    "properties": {"sql": {"type": "string", "description": "A single SQL statement."}},
    "required": ["sql"],
    "additionalProperties": False,
  },
}
  • Be prescriptive about when to call it, not just what it does. The trigger condition belongs in the tool's own description, not only the system prompt.
  • strict: True guarantees the input validates against the schema. It requires additionalProperties: False and an explicit required list.
  • State the guard in the description too — the agent then avoids the rejection rather than discovering it.
Correction to CLAUDE.md § Experiment hygiene

The controls list says “same temperature.” On current Claude models temperature, top_p and top_k are no longer accepted — passing them returns a 400. Temperature cannot be held fixed because it cannot be set.

The replacements are output_config={"effort": …} and the thinking setting; those are what must be identical across modes. Pin the exact model id and log it per run. Verify against the current tool-use docs for whichever model you pin.

6 · Why this is a research point, not plumbing

Anthropic's own agent-design guidance says a bash tool gives the harness only an opaque command string, whereas promoting an action to a dedicated tool gives it “an action-specific hook with typed arguments it can intercept, gate, render, or audit” — and names the criterion for doing so:

“Reversibility is a useful criterion: hard-to-reverse actions … can be gated behind user confirmation.”

The tool-design literature already treats irreversibility as what decides where a boundary goes. This project measures what changes when the action becomes reversible instead — the same idea approached from the other side. That connection belongs in the write-up.
