The Four Restore Mechanisms

Four competing ways to build one feature: undo. You pick one and Mode B is built out of it. They are alternatives, not stages.

The ladder

Think about undoing work on a document. The four mechanisms sit on a ladder from narrow and fast to broad and slow.

MechanismDocument analogyMeasured p50
Savepoint The editor's built-in Ctrl+Z — it already tracks changes, undo walks them back 0.209–0.646 ms
Replay-prefix Delete the file, open the blank template, retype every change worth keeping 6.4–9.4 ms
mysqldump + reload Save a full copy as text; to undo, open the copy 105 ms
docker commit Snapshot the whole computer; restore the entire machine image 510 ms

Savepoint is fastest because it restores the least. That trade — coverage against cost — is the whole comparison.

1 · Savepoint

InnoDB already keeps an undo log for every open transaction, because it needs one for crash recovery. A savepoint just marks a position in that log. Restoring walks the log backwards to the mark.

START TRANSACTION;
SAVEPOINT sp1;                       -- mark a position. Free.
UPDATE `game_results` SET ...;       -- speculative
ROLLBACK TO SAVEPOINT sp1;           -- walk it back

Restores: rows changed in this transaction, in this session.
Misses: anything DDL touched, the filesystem, process memory, other sessions.
Cost driver: rows dirtied since the mark — not table size.

Its fragility

Any DDL, any COMMIT, any BEGIN, or a dropped connection destroys it silently. See Reference 01. This is the price of borrowing a structure the engine maintains for its own purposes.

2 · Replay-prefix

Never undo anything — rebuild from scratch. Keep a list of the statements the agent has decided to keep. To restore: throw the database away, recreate it from the task's initial state, then re-run that list.

# the agent has accepted: [stmt1, stmt2, stmt3]
# stmt4 turned out to be wrong. To get back to the state after stmt3:

DROP DATABASE bench;  CREATE DATABASE bench;
CREATE TABLE `game_results` (...);        -- the 44 original rows
INSERT INTO `game_results` VALUES ...;
# then replay the prefix
stmt1; stmt2; stmt3;

“Prefix” = the front portion of the action list, up to the branch point. The bad statement is simply never replayed.

Restores: the whole database.
Misses: filesystem outside the database, process memory.
Cost driver: the fixed rebuild, mostly. Measured ≈ 6.4 ms + 0.15 ms × k for k replayed statements — so the rebuild dominates until k ≈ 42. Zero storage cost, which is its real appeal.

3 · mysqldump + reload

Ask MySQL to write the entire database out as a text file of SQL statements. To restore, feed that text back in.

mysqldump -uroot -ppw bench > snapshot.sql     # checkpoint
mysql    -uroot -ppw bench < snapshot.sql      # restore

Restores: the whole database, logically.
Misses: process memory, container state.
Cost driver: spawning two processes and serialising through text. At 44 rows the data is irrelevant — the 105 ms is almost entirely process startup.

4 · docker commit

Your MySQL server runs inside a Docker container (dbbench-mysql). A container has a filesystem; docker commit freezes that filesystem into a reusable image. Restoring means starting a fresh container from the frozen image.

docker commit dbbench-mysql snap:v1            # checkpoint
docker run -d --name restored snap:v1          # restore

Restores: the entire container filesystem — database files, config, logs.
Misses: process memory (that needs CRIU, which is what the paper benchmarks).
Cost driver: copying filesystem layers. 510 ms measured, n=3.

Choosing

MechanismStorage costSurvives DDL?Survives reconnect?Verdict here
SavepointNoneNoNo Fastest by 30×. Fragile — needs the action guard from Reference 02
Replay-prefixNoneYesYes Robust fallback. Good second mechanism for a cost-not-truthfulness comparison
mysqldumpOne file per checkpointYesYes Dominated — slower than replay-prefix with no added coverage
docker commitOne image layer eachYesYes Only if you need state outside the database. You do not

Savepoint and replay-prefix are the live pair. Both restore correctly, so comparing them varies cost without varying truthfulness — the clean control from Reference 02. The other two exist mainly to show what generality costs.
